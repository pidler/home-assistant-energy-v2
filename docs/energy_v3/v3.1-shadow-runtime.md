# ENERGY V3.1 HAEO shadow runtime

## Scope

The runtime observes HAEO and live Home Assistant telemetry, evaluates the existing
pure V3 controller and publishes diagnostics. It never controls an inverter, changes
a mode, registers physical ownership or writes an ENERGY V2/HAEO/legacy entity.

## HAEO conversion

Inputs:

- `sensor.optimizer_status` (`success` required, `last_run` must be current);
- `sensor.optimizer_forecast_horizon.attributes.forecast` (193 boundaries);
- `sensor.battery_solax_active_power.attributes.forecast` (192 kW values);
- `sensor.battery_deye_active_power.attributes.forecast` (192 kW values).

For `boundary[i] <= now < boundary[i+1]`, the adapter builds a target with those
exclusive interval boundaries and multiplies both power values by 1000. Signs are
preserved: positive is discharge and negative is charge. Every timestamp must be
timezone-aware, all series must align, intervals must be exactly 900 seconds, and
all powers must be finite. Invalid, stale or inconsistent data fails closed.

## Telemetry and safety

The adapter uses the verified entities encoded in `telemetry_adapter.py`. SolaX
battery power and `sensor.battery_power_otoceny` already use the ENERGY convention:
positive charge and negative discharge. `sensor.solax_measured_power` is converted
to a nonnegative PCC export magnitude with `max(value, 0)`.

The raw DEYE battery sensor is checked against the normalized sensor. The DEYE
inverter AC-power sign is not used in safety calculations. Manual and legacy modes
are published as observations and never treated as V3 writer conflicts.

No verified SolaX fault entity exists. Missing fault evidence is explicit and
fail-closed. DEYE fault evidence combines its battery fault, battery alarm and
device-fault entities.

## Diagnostics

The runtime publishes only these AppDaemon-created sensors:

- `sensor.energy_v3_shadow_haeo_interval`;
- `sensor.energy_v3_shadow_solax_target`;
- `sensor.energy_v3_shadow_deye_target`;
- `sensor.energy_v3_shadow_decision`;
- `sensor.energy_v3_shadow_rejection_reason`;
- `sensor.energy_v3_shadow_telemetry`;
- `sensor.energy_v3_shadow_export_authorization`.

Targets remain visible even when execution is rejected. HAEO adapter errors,
missing export authorization, unsupported capability and other safety reasons have
distinct diagnostic states.

## Later supervised shadow deployment

Do not perform these steps as part of implementation or CI. During an explicitly
approved maintenance window:

1. Confirm the deployed Python files exactly match `deploy/appdaemon/apps/energy_v3/`.
2. Copy `energy_v3_shadow.yaml.disabled` as `energy_v3_shadow.yaml`; keep the
   disabled source template unchanged.
3. Confirm the YAML contains only `EnergyV3ShadowApp` and its timing parameters.
4. Start/reload only under supervision and verify the seven diagnostic sensors.
5. Confirm no inverter, ENERGY V2, HAEO or legacy entity changed.
6. Remove the active YAML to roll back the shadow runtime.

This procedure activates diagnostics only. It does not authorize physical control.
